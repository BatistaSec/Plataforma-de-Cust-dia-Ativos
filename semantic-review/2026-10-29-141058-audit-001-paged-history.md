# Consulta paginada de histórico de auditoria (AUDIT-001)

O audit-service ganhou dois novos endpoints — `GET /api/v1/audit/order/{id}` e `GET /api/v1/audit/portfolio/{id}` — que agora aceitam paginação e filtros opcionais de `eventType` e janela temporal. A mudança introduz um `AuditLogFilter` que valida os limites no construtor, um `Page<T>` de domínio sem dependência de Spring Data, índices compostos na tabela `audit_logs`, e um `GlobalExceptionHandler` enriquecido. Os endpoints antigos foram **substituídos** no lugar, não mantidos em paralelo, o que quebra contrato com qualquer cliente que esperava um array JSON puro.

**Watch for:** quebra de contrato no response body (confirmed); `AuditLogFilter` importado pelo domínio viola Clean Architecture (confirmed); query JPQL com enum nullable apresenta bug conhecido no Hibernate 6 com certos dialetos (likely); handler 500 vaza `ex.getMessage()` em produção (confirmed); nenhum teste unitário ou de integração cobre qualquer caminho introduzido por esta mudança (confirmed).

**Verdict**: NEEDS_CHANGES

---

## High-level view

O controller substituiu as assinaturas de retorno de `List<AuditLogOutput>` para `PagedAuditResponse` diretamente nos mesmos paths, sem versionamento de API nem período de compatibilidade. Clientes que deserializam a resposta como array JSON recebem agora um objeto com envelope de paginação — quebra silenciosa e sem deprecation warning.

O `AuditLogFilter` vive em `application.dto` mas é referenciado pela interface `AuditLogRepository` no pacote `domain.repositories`. Isso inverte a hierarquia de dependência da Clean Architecture: o domínio passa a depender da camada de aplicação.

A query JPQL usa `:param IS NULL OR e.eventType = :eventType` com um parâmetro do tipo enum. No Hibernate 6 (usado pelo Spring Boot 3.x) esse padrão pode falhar para parâmetros de enum anuláveis dependendo do dialeto configurado — o Hibernate pode não conseguir inferir o tipo SQL do binding quando o valor é `null`.

A cobertura de testes se resume a um `contextLoads()`. Nenhum dos cenários novos — validações do filtro, comportamento do `Page` em edge cases, mapeamento JPQL — está testado.

<details>
<summary>Issues (6)</summary>

1. **Quebra de contrato no response body** — Os endpoints `/order/{id}` e `/portfolio/{id}` agora retornam um objeto `PagedAuditResponse` em vez do array JSON que retornavam antes. Clientes existentes que deserializam como `List<AuditLogResponse>` quebram sem aviso. Solução: versionar os novos endpoints em `/api/v2/audit/...` e manter os `/v1` originais, ou documentar e coordenar a migração antes do deploy.

2. **Domínio importando camada de aplicação** — `AuditLogRepository` (domínio) importa `AuditLogFilter` (application.dto). A dependência deveria ser ao contrário. Mova `AuditLogFilter` para `domain.query` ou `domain.criteria`, ou defina uma interface no domínio e deixe o DTO de aplicação implementá-la.

3. **Bug potencial na query JPQL com enum nullable** — `:eventType IS NULL OR e.eventType = :eventType` pode lançar `IllegalArgumentException` ou produzir resultado errado no Hibernate 6 quando `eventType` é `null`, porque o Hibernate não consegue inferir o tipo JDBC de um binding nulo de enum. Solução: usar `@Query` com SpEL condicional, separar as queries por presença/ausência do filtro, ou usar `Criteria API`.

4. **Use cases legados injetados mas nunca usados** — O controller injeta `GetAuditLogsByOrderUseCase` e `GetAuditLogsByPortfolioUseCase` via construtor mas nunca os chama. São dead code no grafo de dependência. Remova as injeções se os endpoints não-paginados foram intencionalmente descartados.

5. **Vazamento de informação no handler 500** — O fallback genérico expõe `ex.getMessage()` no campo `detail` da resposta. Em produção, mensagens de SQL, nomes de classes internas e detalhes do Hibernate ficam visíveis no response body. Omitir o campo ou substituí-lo por um ID de correlação logado server-side.

6. **Zero cobertura de testes para código novo** — Nenhum teste unitário cobre `AuditLogFilter` (validações de limite, inversão de `from`/`to`), os dois use cases paginados, nem o `GlobalExceptionHandler`. Adicione testes unitários para o filtro e o record de paginação, e ao menos um teste de integração com banco em memória para verificar o comportamento da query JPQL com `eventType=null`.

<details>
<summary>Details</summary>

### Quebra de contrato: array JSON → envelope paginado

Os endpoints `GET /api/v1/audit/order/{orderId}` e `GET /api/v1/audit/portfolio/{portfolioId}` existiam antes desta mudança e retornavam algo mapeado a partir de `List<AuditLogOutput>`. O controller agora retorna `PagedAuditResponse` nesses mesmos paths com a mesma versão de API. Qualquer cliente — o api-gateway, testes de contrato, integrações externas — que esperava um array JSON raiz recebe agora:

```json
{
  "content": [...],
  "page": 0,
  "size": 20,
  "totalElements": 3,
  "totalPages": 1,
  "first": true,
  "last": true
}
```

A mudança é confirmed porque os endpoints têm o mesmo path e método HTTP, e o tipo de retorno do controller foi alterado de `ResponseEntity<List<...>>` para `ResponseEntity<PagedAuditResponse>`. Não há versionamento, redirect, nem content-negotiation.

Vale notar que os dois use cases legados (`GetAuditLogsByOrderUseCase`, `GetAuditLogsByPortfolioUseCase`) ainda são injetados no construtor do `AuditController` mas não aparecem em nenhum `@GetMapping`. São beans carregados, wired, e nunca invocados.

### Violação de camada: `AuditLogRepository` depende de `application.dto`

```
domain.repositories.AuditLogRepository
    imports application.dto.AuditLogFilter   ← dependência invertida
```

Na Clean Architecture, o domínio é a camada mais interna e não deve conhecer nada de `application`. `AuditLogFilter` pertence conceitualmente ao domínio (é um critério de busca, não um caso de uso), então a solução mais simples é movê-lo para `domain.query` ou `domain.criteria`. Alternativamente, defina uma interface `AuditQuery` no domínio e faça `AuditLogFilter` implementá-la na camada de aplicação — mas isso adiciona indireção sem benefício real aqui.

### Bug potencial na query JPQL com enum nullable

```java
AND (:eventType IS NULL OR e.eventType = :eventType)
```

No Hibernate 6, quando `:eventType` é `null`, o binding é feito sem tipo explícito. Para parâmetros de enum, o Hibernate precisa saber que o tipo esperado é `AuditEventType` para gerar o SQL correto. Com valor `null`, alguns dialetos (especialmente H2 em testes e PostgreSQL em certos modos) lançam `IllegalArgumentException: Parameter value [null] did not match expected type`. O comportamento depende da versão exata do Hibernate e do dialeto. A forma segura é separar as queries com um método auxiliar que decide qual query chamar baseado na presença do filtro, ou usar `Criteria API`.

Este é um risco **likely** — não há evidência direta de falha nos logs existentes, mas o padrão é amplamente documentado como problemático no Hibernate 6.

### Índices compostos e path sem subject

Os índices `idx_audit_portfolio_occurred (portfolio_id, occurred_at DESC)` e `idx_audit_order_occurred (order_id, occurred_at DESC)` cobrem o caso principal da query. Quando ambos `portfolioId` e `orderId` forem nulos — possível chamando `findPaged` diretamente com um `AuditLogFilter` cujo `subjectId` seja nulo — a query faz full table scan com apenas `eventType`/tempo como filtro. O controller nunca produz esse estado, mas a porta está aberta no repositório.

### Vazamento de informação no handler 500

O fallback genérico do `GlobalExceptionHandler` expõe `ex.getMessage()` no campo `detail` da resposta 500. Dependendo da exceção — SQL com detalhes de schema, nomes de classes internas, mensagens do Hibernate — isso vaza informação estrutural da aplicação. Em produção esse campo deveria ser omitido ou substituído por um ID de correlação logado server-side.
